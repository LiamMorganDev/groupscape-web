# Update OSRS data

GroupScape's item and boss data is a static, hand-maintained snapshot — there's no live fetch at runtime. This skill refreshes it from the OSRS Wiki. Item updates are mechanical; boss updates need judgment (is this new NPC "notable" enough for the activity feed? does it need a curated drop table?), so this skill does the mechanical part with scripts and the judgment part itself.

## Steps

1. **Fetch item data.** Run `npm run update-items` inside `site/` (`site/scripts/osrs-data/fetch-items.mjs`). This pulls the OSRS Wiki pricing API's item mapping, diffs it against `site/public/data/item_data.json`, updates changed/new entries, downloads+converts new icons to `site/public/icons/items/<id>.webp`, and mirrors the result to `server/src/content/item_names.json` (must stay byte-identical — the Rust server embeds it via `include_str!`). Report what changed: items added/updated, icons fetched, any download failures.

2. **Refresh the Discord icon map.** Whenever step 1 added or renamed any items, also run `npm run update-item-icons` inside `site/` (`site/scripts/osrs-data/fetch-item-wiki-icons.mjs`). This resolves every item's real wiki `File:` page (following redirects) into `server/src/content/item_wiki_icons.json` - the verified id → icon-filename map `discord::item_icon_url` uses for Discord notification thumbnails, so new/renamed items get a correct thumbnail instead of falling back to a name guess. Takes a few minutes (one batched wiki API request per ~50 item names). Report how many item ids resolved vs. total, and any batch failures.

3. **Detect boss/NPC candidates.** Run `npm run detect-bosses` inside `site/` (`site/scripts/osrs-data/detect-new-bosses.mjs`). This is read-only — it scans the wiki's boss category against `site/src/data/boss-levels.js`'s `BOSS_COMBAT_LEVELS` and reports candidates not yet tracked, with combat level and whether wise-old-man already has a hiscore-style icon for it.

4. **Classify each candidate boss.** For every candidate in the report:
   - Decide if it belongs in `NOTABLE_NPCS` (`server/src/notable_npcs.rs`) — i.e. is it a real boss/quest-boss worth surfacing in the group activity feed, not feed noise (regular monsters, reused generic NPC names). Ask the user via `AskUserQuestion` when it's ambiguous (e.g. a minigame boss, a reused generic-sounding name).
   - If notable, add its slug to `NOTABLE_NPCS` and add a `slug: combatLevel` entry to `BOSS_COMBAT_LEVELS` in `site/src/data/boss-levels.js` — keep these two lists in sync, matching the existing hand-curated style and ordering in both files.
   - Only add a `drop_rates.json` entry (`server/src/content/drop_rates.json`) if the boss should get curated loot-rarity display in the loot log — this is a bigger, separate curation effort (item id → name/rarity/isUnique/rate per drop), not something to rush through automatically. Ask the user whether they want to do this now for a given boss, or leave it for later.
   - When adding or extending a `drop_rates.json` entry, also try to fill in `rate` (a wiki-sourced fixed per-kill fraction, e.g. `"1/508"`) for each item — but only when the wiki shows one genuine simple fixed roll for that item from that specific boss. Leave `rate` unset (never guess) for anything gated by points, team size, thresholds, or a shared reward-pool/one-of-many mechanic (raid uniques, Barrows, Wintertodt/Tempoross-style pools, Gauntlet-style reward chests) — those don't reduce to a single fraction. Items only obtainable via the shared Rare Drop Table/Gem Drop Table are ambiguous (the wiki gives the RDT's own odds, not this boss's chance of rolling into RDT at all) — treat as unconfirmable unless the boss's own page states a combined per-kill rate for that item directly. A 2026-09 backfill pass (6 parallel research agents, one per batch of ~9-10 bosses, each reading the boss's own wiki drop-table section and writing verified rates) took curated `rate` coverage from 810/2240 items (36%) to 1678/2240 (75%) across 57 bosses; the remaining gaps are mostly RDT-derived or ambiguous multi-row items that weren't confirmable from a single wiki table row.
   - **Every boss with a `drop_rates.json` entry should also have its pet's item id in that entry** (`"isUnique": true`, plus `rate` when the wiki states one clean fixed fraction for that boss specifically — same never-guess rule as above; a fair number of pets are simple fixed rolls, but some use different mechanics, so verify each one on the wiki rather than assuming). A new notable boss with a pet should get this in the same pass as its main drop_rates.json entry, not deferred. A 2026-09 pass (one research agent verifying each boss's pet against its own wiki page/the pet's wiki "Sources" section) backfilled pet entries for the ~70 bosses that had a `drop_rates.json` entry at the time.
   - Add the icon: if wise-old-man already has it (per the report), download `https://raw.githubusercontent.com/wise-old-man/wise-old-man/master/app/public/img/metrics/<slug>.png` to `site/public/icons/hiscore/bosses/<slug>.png`. Otherwise, fetch the boss's wiki infobox image and resize/convert to a 25×25 PNG with `sharp` to match the existing icon set's dimensions. Add the slug to `BOSS_ICON_SLUGS` in `site/src/data/boss-icons.js`.

5. **Detect new quests.** Run `npm run detect-quests` inside `site/` (`site/scripts/osrs-data/detect-new-quests.mjs`). Read-only — it scans every wiki page carrying a quest infobox against `site/public/data/quest_data.json`'s names and reports titles not yet tracked. Expect some noise: miniquests may legitimately not belong in `quest_data.json` (RuneLite's `quests` byte array only covers full quests - see `quest_ids.rs`), so treat each candidate as a question, not an automatic add. For each real miss, add an entry to `quest_data.json` (and mirror to `server/src/content/quest_data.json`, which must stay byte-identical per `quest_ids.rs`'s doc comment) with its id (RuneLite's `QuestState`-array index - check the plugin's `Quest` enum ordinal, not the wiki), name, difficulty, and points.

6. **Detect new combat achievement tasks.** Run `npm run detect-ca-tasks` inside `site/` (`site/scripts/osrs-data/detect-new-ca-tasks.mjs`). Read-only — same pattern as step 5, against every task name in `server/src/content/combat_achievement_tasks.json`. For each real miss, add it under the right tier with its id (RuneLite's internal CA task id, not derivable from the wiki - check the plugin/`combat_achievement_content.rs`'s existing entries for the numbering convention) and boss.

6a. **Refresh combat achievement completion %.** `server/src/content/combat_achievement_completion.json` (task id → wiki-crowdsourced "Comp%", used by the Discord combat-achievement notification's "Completed by" field) is a point-in-time scrape, not a live fetch, so it drifts as more accounts complete tasks over time. Whenever step 6 added new tasks, or it's just been a while (this isn't detectable automatically - ask the user if unsure, or just do it whenever running this skill for an unrelated reason and it hasn't been refreshed recently):
   - Fetch `https://oldschool.runescape.wiki/api.php?action=parse&page=Combat_Achievements/All_tasks&prop=text&format=json`, find the `<table ... class="... ca-tasks">` in the returned HTML, and parse every `<tr data-ca-task-id="N">...<td class="table-bg-...">P%</td></tr>` row — the `data-ca-task-id` is the game's own task id (matches `combat_achievement_tasks.json`'s `id` field directly, no name-matching needed) and `P` is the Comp%.
   - Overwrite `combat_achievement_completion.json` with the freshly parsed `{ "taskId": percent, ... }` map (sorted by numeric id for a clean diff).
   - Run `cargo test combat_achievement_content` in `server/` - it asserts every task in `combat_achievement_tasks.json` has a completion% entry, which also catches step 6 having added a task this scrape doesn't cover yet (the wiki table may lag brand-new tasks briefly; that's fine, just note it rather than blocking).

6b. **Detect new/changed achievement diary tasks.** Run `npm run detect-diary-tasks` inside `site/` (`site/scripts/osrs-data/detect-new-diary-tasks.mjs`). Read-only - diary tasks have no per-task wiki infobox to diff like quests/CA tasks do, so this instead fetches each area's `<Area> Diary` wiki page and counts the numbered task rows in each tier's table, flagging any area/tier where that count doesn't match `diary_data.json[area][tier].length`. A mismatch means a task was added, removed, or split on the wiki - open the flagged area's wiki page, compare tasks by hand, and update `diary_data.json` (task text plus `requirements.quests`/`requirements.skills`, matching existing entries' shape). Note this only catches count changes, not a same-count task reword (e.g. a task retargeted at a renamed/reworked boss) - worth an occasional manual reread of a diary page even on a clean report, especially after a relevant game update.

6c. **Detect new slayer task types.** Run `npm run detect-slayer-tasks` inside `site/` (`site/scripts/osrs-data/detect-new-slayer-tasks.mjs`). Read-only - it reads the canonical task name off every monster page's `{{HasTask|<name>}}` wiki template and flags any name not covered (allowing for the site's own singular/plural fallback) by `SLAYER_MONSTER_ICONS` in `site/src/data/slayer.js`. For each real candidate: add it to `SLAYER_MONSTER_ICONS` with a local icon key, fetch/convert its wiki icon the same way step 4 handles boss icons, and - if it's one of the generic "Boss" task's assignable bosses - add it to `BOSS_TASK_NAMES` in `server/src/slayer_boss_tasks.rs` too (its own comment says to keep these two lists in sync manually; do it in the same pass, not deferred).

7. **Validate.** Run `npm test -- cache-data.test.js` in `site/` and `cargo test notable_npcs` in `server/`. Fix anything that fails before continuing.

8. **Commit.** Use the `commit` skill (this repo's scoped one, not a bare `git commit`) to commit the changes with a real CHANGELOG.md entry — describe it in player-facing terms (e.g. "Added support for tracking <Boss Name> kills and drops") or as an internal data-refresh entry if nothing changed user-facing this run.

## Notes

- The item mapping endpoint only covers GE-tradeable items (~4,000 of ~19,500). Non-tradeable additions (most quest items, some cosmetics) won't be caught by `update-items` — if the user mentions a specific non-tradeable item is missing, add it to `item_data.json` (and mirror to `item_names.json`) by hand, then also add it to `item_wiki_icons.json` by resolving its real `File:` page the same way step 2's script does (or just re-run that script - it covers every item in `item_data.json`, tradeable or not).
- There is no CI gate on this data anymore (`.github/workflows/cache-validation.yml` was removed) — the `npm test`/`cargo test` step in this skill is the only validation, so don't skip it.
- **Collection log pages** (`server/src/content/collection_log_info.json` / `site/public/data/collection_log_info.json`) have no automated detector — the wiki has no reliable structured listing of collection log pages to diff against (unlike quests/CA tasks/bosses, which each have their own infobox template to query). The one dependable trigger is step 4: a newly-notable boss usually ships with its own collection log page, so check for one (and its item list) whenever a candidate boss is accepted there. Outside of that, only act on it if the user reports a specific missing page/item.
- **Drop rate coverage is still partial.** As of the 2026-09 backfill pass (step 4), curated `rate` coverage sits at 1678/2240 items (75%) across 57 bosses in `drop_rates.json`; the rest are RDT-derived or ambiguous multi-row items unconfirmable from a single wiki table row at the time. Since the wiki fills in more standalone per-boss rates over time (e.g. a table row gets clarified, or a shared-pool mechanic gets a boss-specific rate published), it's worth periodically re-checking `rate: null`/missing entries for bosses already in `drop_rates.json` against their current wiki drop table - same never-guess rule as step 4 applies. Not automatic (no detector), just a standing thing to do a pass over occasionally or when the user asks.
- **Equipment set bonuses** (`site/public/data/set_bonuses.json` / `target_bonuses.json`) change a few times a year (new BiS gear sets) and have no automated detector either - this is judgment-heavy (deciding/verifying the actual bonus values, not just noticing a new set exists), so treat it as a standalone ask rather than folding it into this skill's mechanical steps.
- **Clue casket rewards have no `drop_rates.json` coverage** (as of 2026-09) - unlike a boss's main drop table, the wiki expresses clue rewards as weight-in-a-shared-table rather than a clean per-open fraction for most items, so the Discord clue-casket "rare reward" callout (`discord::rarest_probability` reused against `loot_event.source_name`) is currently a no-op for every clue tier. Only add clue entries if the wiki states a genuine standalone fixed rate for a specific clue-tier reward (rare, but do check rather than assuming none exist) - never convert a table weight into a rate yourself.
